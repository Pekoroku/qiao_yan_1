# Jiang Qiao Yan｜油画作品集网站
## Astro 开发交接说明、执行规则与目标验收标准 v1.0

日期：2026-09-22
用途：交给后续 AI 或开发者，作为需求基线、实现约束和验收依据。
文档状态：开发要求，不是已经完成开发或通过测试的证明。

> 建立一个完整、有艺术辨识度、便于欣赏和理解油画作品的多页面静态网站。以真实浏览体验、图像质量、加载成本和维护能力验收，不能以“代码写完”“页面存在”或“截图好看”代替目标完成。

## 1. 已确定事实、暂定方案与需求优先级

### 1.1 已确定

- 艺术家展示姓名为 **Jiang Qiao Yan**。不得自行推断中文姓名、姓名缩写、身份履历或另一个品牌名称。
- 网站展示油画作品，预计约 40–50 幅，之后可能增加。不能只按 6 幅演示内容设计。
- 网站必须包含首页、作品总览、每幅作品的独立详情页。作品详情需支持大图、标题、时间、创作背景、心境与故事。
- 当前正式图片、标题、完整创作说明、艺术家介绍和联系方式尚未收齐；允许先完成结构和占位演示。
- 视觉需要有艺术氛围和辨识度，不能停留在“安全但普通”的通用艺术网站模板。
- 后续正式视觉应从真实油画的主题、色彩、笔触、构图和观看方式发展。
- 要考虑中国大陆访问体验、移动端体验、图片大小、流量成本和托管迁移。
- 默认采用 Astro 多页面静态生成，不增加没有必要的运行时后端。
- 图标采用统一 SVG，不使用容易被系统渲染为 emoji 的字符。
- 开发者必须具备“验证结果—发现问题—修复—回归测试”的闭环。

### 1.2 暂定、不能当成客户已批准的设计

纸白、深墨绿、氧化红配色，大号衬线姓名，Room to Look 文案，错位排版，展览／目录双视图，以及页面展开效果，均属于此前原型或候选设计，不等于正式品牌规范。

快速预览、双视图、多语言切换、超高清放大、独立展览页和复杂页面过渡是可选增强。不能为了实现所有候选功能而破坏核心体验或增加不必要依赖。

本文件中的图片尺寸、体积预算、动效时长和测试样本数是建议工程基线，可依据真实素材调整，但调整必须说明代价，不能静默放宽。

### 1.3 优先级与冲突处理

- **P0：上线阻断项。** 核心浏览链路、作品独立地址、静态部署、手机可用性、图像不被错误裁切、母版不公开、必要字段校验和严重故障处理。
- **P1：正式交付要求。** 艺术语言、动效细节、性能预算、可访问性、维护文档、跨端验证和部署验证。未通过项需明确披露并由项目方确认处理方案。
- **P2：可选增强。** 双视图、快捷搜索、复杂过渡、快速预览、超高清放大等。

出现冲突时，先保作品真实呈现和主要浏览路径，再保性能与可维护性，最后决定装饰性动效。用户后续明确确认的要求优先于本文的默认建议；所有变更应记录。

## 2. 成功标准：要完成什么目的

| 目标 | 真正完成的表现 | 不算完成的情况 |
|---|---|---|
| 认识艺术家 | 访客能辨认姓名、理解这是作品集并找到作品入口 | 姓名被裁切，首页只有抽象装饰 |
| 浏览全部作品 | 40–50 幅作品均可发现，作品排列有节奏且便于寻找 | 只做首页和少量卡片 |
| 阅读单幅作品 | 作品有独立地址，大图、资料、创作故事构成完整阅读空间 | 只有大图弹窗，故事没有位置 |
| 艺术辨识度 | 视觉决策能与真实作品的主题或观看需求对应，并通过视觉评审 | 仅凭“留白＋衬线字”自行宣称高级 |
| 控制加载成本 | 网络记录证明首屏未下载全站大图，用户按需获取图像 | 只写了 lazy 属性，实际大图照样全下载 |
| 长期维护 | 新增一件作品后，相关页面和导航自动更新 | 每加一幅画都要复制修改网页 |
| 可靠交付 | 有构建、浏览器、失败场景与部署证据，未测试项明确标注 | 只说“理论上支持”“应该没问题” |

## 3. 页面结构与内容职责

推荐路由：

```text
/
/works/
/works/<stable-slug>/
/about/
/contact/
/exhibitions/             # 有足够真实资料时才发布
/404.html
```

### 3.1 首页

首页负责第一印象和导览，不承担完整作品库。

必须包含艺术家姓名、代表作展示位置、清晰的全部作品入口，以及适量精选作品／艺术家介绍入口。精选数量可从 4–8 件起步，依据构图调整，不在首页铺满 50 幅大图。

主按钮“浏览全部作品／Explore works”默认链接到 `/works/`。如果另设首页内滚动入口，应使用不同且准确的名称，例如“查看精选作品”。点击首页主作品进入该作品的独立详情。

不强制等待开场动画，不用弹窗或加载遮罩阻挡进入网站。

### 3.2 作品总览 `/works/`

必须展示全部已发布作品，每件作品可进入自己的详情页。以统一数据源生成，不人工重复维护作品清单。

默认视图需兼顾油画原始比例、作品辨识和移动端滚动效率。展览视图可有大小与留白变化；目录视图可更规整。双视图不是必须同时做。

系列、年份筛选应在真实数据具备时启用。没有有意义的分类，不硬凑筛选项。筛选需显示当前状态、结果数量、清除入口和空结果反馈。

40–50 件作品无需默认采用复杂分页或无限滚动。先实现可完整访问的静态列表和按需图片加载，数量增长后再根据测试决定。

### 3.3 单幅作品详情 `/works/<stable-slug>/`

每件作品必须有真正可直接访问、刷新、复制和分享的独立页面。详情不是只能通过首页或弹窗进入的临时状态。

内容结构支持：

1. 完整构图的网页展示图及作品标题。
2. 年份／日期、媒介、实体尺寸及单位、系列。
3. 创作主题、背景、创作时的心境、过程与故事；长文可分段和加小标题。
4. 局部细节图及说明，有资料才展示。
5. 上一件、下一件、返回全部作品；相关作品为可选项。
6. “只看画作”模式；需要时增加明确的高清细节加载入口。

以上是内容能力要求，不意味着缺资料时可以编造文本。正式页面不展示未批准的“待补充”故事，不把未知年份自动填成当前年份。缺少可选字段时，整段自然收起。

详情页应允许正常滚动阅读。长故事不能被锁在狭小弹窗或固定高度面板中。

### 3.4 关于、联系与展览

关于页支持真实简介、创作理念、照片和经历；联系页支持批准公开的邮箱或社交信息。联系表单不属于默认范围，不能显示会假装提交成功的表单。

展览资料不足时，不发布一个空的展览页面。可先在关于页预留数据结构，资料到齐后再决定独立页面。

### 3.5 默认不做的范围

注册登录、会员权限、评论、购物车、支付、订单管理、运行时数据库、云端收藏和在线上传后台均不在当前范围。

作品编辑默认通过内容文件与重新构建完成。未来需要在线编辑时再评估 CMS；不能为了未来可能性提前增加账号系统和服务器。第三方表单、支付或 CMS 可能提供后台服务，但那不属于当前纯静态交付。

## 4. 导航、滚动、历史记录与已知问题

### 4.1 已观察／已报告问题

- 用户的 iPhone 截图中，箭头显示为蓝色 emoji。
- 用户报告“进入作品”跳转的位置不符合预期。

这是必须验证并消除的问题；截图和报告不能代替对旧代码根因的复现，不得未经检查就断言是某一个固定 CSS 或 JS 原因。

### 4.2 导航规则

使用真实链接作为页面导航基础。普通点击、新标签页打开、复制链接、刷新、浏览器后退／前进都必须有正确行为。不要只给卡片绑定 click 而不提供实际 href。

默认“点击作品”直接进入详情页；快速预览可选，不能成为阅读详情的强制额外步骤。

从总览进入详情后，浏览器后退应恢复原有筛选、视图和接近原位置的作品上下文。直接从外部链接打开详情时，“返回作品”需稳定回到总览，不盲目执行 history.back() 返回站外。

上一件／下一件默认按全站已发布作品的明确排序；若另做“当前筛选结果中的上一件／下一件”，必须清楚说明并测试边界。不要悄悄混用两个顺序。

### 4.3 锚点与滚动验收

保留页面内跳转时，以目标标题／内容起点为锚点，考虑真实导航高度、移动菜单收起后的布局、安全区及字体和图片加载后的变化。

`scroll-margin-top` 可作为实现手段，但不是“写上去就算完成”。[S11]

不得使用固定延时硬凑定位，不在每次图片加载后强制把用户拉回顶部。验收时，目标标题和内容起点应可见，不被固定导航遮住，不落在无意义大留白里，也不在加载后再次跳走。

## 5. 艺术方向：从作品发展，而非套模板

### 5.1 当前阶段

现有 Overview 只作为结构原型和方向讨论参考。允许改版，不要求保留现有配色、标题比例或布局。

素材未到时可先完成组件、页面骨架、动作关系和占位布局，但必须标识为概念阶段，不能宣称已完成艺术家正式视觉。

### 5.2 获得素材后的设计方法

先选 6–10 幅能代表主要风格的作品，覆盖横幅、竖幅、明暗、复杂／安静画面，分析主题、构图、色彩、笔触、叙事和适合的观看距离。

再提出 2–3 个简短方向，用同一组真实作品进行对照，不用不同图片制造不公平比较。每个方向说明：页面比例、字体、背景、动效和观看路径怎样服务这组作品。

选定方向后再展开正式页面。不必先把三个方向都开发成完整网站。

### 5.3 视觉底线

- 不默认套仿古画框、泼墨背景、笔刷擦除、粒子、玻璃卡片、霓虹渐变或科技产品落地页结构。
- 不因“这是油画”就到处添加画布纹理；装饰必须有实际作用。
- 允许克制的非对称与编辑式排版，但作品标题、导航和阅读顺序必须清楚。
- 默认保留完整画面比例，不能为对齐卡片把所有作品裁成正方形。
- 首页艺术化裁切如确有需要，须明确批准，且随时可进入完整图。
- 不对正式作品添加改变色彩的滤镜、混合模式、透明蒙层或动态扭曲。
- 辅助色可以来自作品，作品观看区域仍需检查背景对色彩判断的干扰。

视觉评审需有项目方确认；自动化测试或开发者自评“高级”不能替代审美验收。

## 6. 字体、图标和界面一致性

### 6.1 SVG 图标系统

所有交互箭头、关闭、上一件／下一件、展开、菜单、返回、外链等，统一使用 SVG 组件。

默认用内联 SVG 或本地 SVG，不使用 Unicode 箭头作为 UI 图标，不使用 emoji、不依赖系统图标字体，也不为简单箭头改用 PNG。SVG 支持以 viewBox 建立缩放坐标体系，适合这套图标实现。[S9]

建议规范：统一 24×24 viewBox、少量固定显示尺寸、1.5–2 的描边基线、统一端点与转角、currentColor 随主题变化。高分屏检查视觉清晰度和描边，不承诺所有浏览器抗锯齿逐像素一致。

纯图标按钮必须有可访问名称；装饰性 SVG 对辅助技术隐藏。图标可小，移动端点击区域按至少 44×44 CSS px 的项目设计目标执行。

### 6.2 字体与文字

艺术家姓名固定为 Jiang Qiao Yan。正式网站语言和是否完整双语仍待确认；先将 UI 文案集中管理，预留中文长标题和英文长单词的空间，不强制中英逐句重复。

中文正文要易读，英文字体与中文标点、数字、行高需实际配对检查。可使用系统字体回退；需要品牌字体时，仅使用许可允许的字体并审查体积。不得把系统字体文件直接从电脑拷贝到网站分发。

关键字体、图标和脚本不依赖第三方字体／脚本 CDN 才能显示。文字不能因自定义字体未加载而长时间不可见。正文建议从 16 CSS px 左右起测，不能为了排版把主要内容做成难读小字。

## 7. 动效规则与渐进增强

动画应解释空间、作品关系或操作反馈，不以数量和复杂度作为艺术感指标。

允许的方向包括：短暂的姓名显现、轻微入场、作品到详情的自然衔接、视图排列过渡、按钮微反馈。界面反馈可先按 120–200 ms、内容过渡按 250–450 ms 起测；这是候选参数，不是已定稿时长。

必须满足：

- 不劫持自然滚动，不强制横向浏览，不用长预加载动画锁住内容。
- 没有鼠标悬停时仍能看到关键资料并完成操作。
- 首屏不能以全站等待 JS 才取消 opacity:0 的方式实现。
- 系统启用减少动态效果时，关闭非必要运动；如提供站内动效开关，应保存偏好并采用更保守设置。[S10]
- 过渡不受支持、脚本失败或动效关闭时，仍可正常通过静态链接访问页面。
- 快速连续点击、返回、切换视图不能造成重复事件、错图、遮罩残留、滚动锁死或重复下载大图。
- 页面间过渡为增强层，不为了做动画把整站变成依赖 JS 的单页应用。

Astro 支持页面过渡方案；是否启用 ClientRouter 或其他机制需按所用版本验证脚本生命周期、历史记录和预取行为，不能只因框架提供功能就全部启用。[S16]

## 8. 图片、图像质量、流量与素材保护

### 8.1 明确“原图”的含义

网页中默认提供的是 **高清展示版**，不是艺术家的存档母版。

母版、TIFF／PSD／RAW、大尺寸印刷源文件和私人资料不进入公开仓库、public 目录或发布产物。建站时使用经批准的网页处理源图；不能先把母版公开再寄希望于隐藏链接。

项目不承诺防截图或防下载，也不以禁止右键作为作品保护方案。能公开展示的图片应按可被保存的前提审批。

### 8.2 分级与响应式尺寸

| 用途 | 初始建议 | 请求时机 |
|---|---|---|
| 总览缩略图 | 按容器生成若干候选，通常约 480–960 px 宽 | 对应卡片接近可见区域时 |
| 首页／详情展示图 | 通常约 1200–2000 px，依据屏幕和作品比例选择 | 当前页实际需要显示时 |
| 高清细节图 | 长边通常约 2560–3500 px，个别作品另评估 | 明确打开细节或放大时 |
| 存档母版 | 保持本地／专用非公开归档 | 不从公开网站提供 |

不要求每幅画机械生成表内每一个尺寸，极长横幅／竖幅需按实际显示宽高处理，也不得放大超过源图有效分辨率。高 DPR 手机需兼顾清晰度与传输量，不能手机默认下载最大图。

优先 WebP，可在画质和体积测试后增加 AVIF，并设置适当 JPEG 回退。通过 picture/srcset/sizes 提供候选，不由 JS 把多种格式都下载一遍。Astro 的 Image/Picture 能用于构建时生成图像；放进 public 的文件不会自动获得同等优化，必须检查输出文件。[S4]

### 8.3 按需加载的硬要求

- 当前页主视觉／首屏关键图不能错误使用延迟加载；首屏外列表图使用懒加载。
- 总览页不能先加载所有详情大图，再用 CSS 把它们缩小。
- 隐藏弹窗、背景层、data 属性处理脚本和路由预取都要审计，防止绕过分级策略。
- 加载详情时，只请求当前作品需要的图；非必要预取默认关闭。
- 高清图仅在明确需要时请求。超大细节图应显示加载反馈，不能让用户无限等待。
- 为图片提供真实宽高／比例，避免页面在加载后跳动。

原生 loading="lazy" 是浏览器调度提示，浏览器可能提前请求视口附近的图片。因此不能以“只加载正好 8 张”为通用验收标准；要看实际选择的分辨率、请求体积，以及是否违规加载高分辨率资源。[S12]

### 8.4 画质与色彩

缩略图与详情需分别人工检查。关注厚涂笔触、暗部、细线、色彩渐变和边缘是否因压缩而损坏，不能仅为了达成 KB 指标把画压糊。

处理源图时采用明确的色彩管理流程；网页衍生图按批准流程转为 sRGB 并检查视觉对照，不能简单删除色彩信息导致明显偏色。移除 GPS 等非必要隐私元数据。原始归档单独保留。

不同设备显示差异不能完全由网站消除；网站不得额外叠加美化滤镜、锐化过量或 AI 生成的假细节。

### 8.5 图像清单

构建阶段应导出 image-manifest：作品 ID、文件路径、用途、宽高、格式、字节数。用于验证缺图、超预算、重复生成、作品图错配和母版泄露。

压力测试不可仅复用同一图片 URL 50 次；浏览器缓存会使测试失真。应覆盖不同尺寸与独立资源路径，报告真实资源数量。

## 9. 数据结构与内容维护

推荐采用 **Astro Content Collections + Markdown 正文 + 结构化元数据**。作品共用模板，构建时生成详情与列表。[S3]

### 9.1 作品字段

| 字段 | 规则 |
|---|---|
| id | 唯一、稳定；禁止重复 |
| slug | 稳定 URL 标识，避免随标题改动自动变化 |
| title | 正式发布必需；多语言标题按需要扩展 |
| year/date | 可选；未知不编造，不与上传时间混淆 |
| medium | 可选；使用客户批准的描述 |
| dimensions | 作品实体尺寸与单位，和图片像素宽高分开 |
| series | 可选；只使用真实分类 |
| order / featured | 控制排序与首页精选 |
| image / width / height | 主图及真实像素尺寸；发布必需 |
| alt | 对作品的适当文字描述；正式发布必需 |
| detailImages | 可选，多张局部图及各自说明 |
| body | 创作背景、心境、过程与故事正文，可长可短 |
| status | 至少区分 draft 与 published |
| isPlaceholder | 区分演示数据，禁止混入正式发布 |

### 9.2 校验与发布

ID／slug 重复、引用图片不存在、图像尺寸无效、发布记录缺必需字段，必须阻止生产构建并输出具体文件位置。

缺可选资料不得导致程序报错，也不能出现 undefined、空分隔符、空标题或大片空模块。错误提示用于维护者，不把构建错误堆栈展示给公众。

数据渲染应使用转义和受控 Markdown，不能直接注入未经审核的任意 HTML。

### 9.3 验证新增维护

必须用实际演练验证新增“第 51 件作品”：增加一个内容文件和图片，构建后总览、独立详情、上一件／下一件、相关索引及站点地图更新，无需手工复制页面。

作品移除或变成 draft 后，不得仍留在精选、相关作品、导航或 sitemap 中。已发布 slug 如需变更，要记录重定向／迁移方案及目标平台是否支持。

## 10. Astro 工程与静态部署约束

### 10.1 架构

采用 Astro 静态生成：output 为 static；全部公开页面预渲染，不允许局部页面偷偷依赖 SSR、数据库或运行时图片 API。动态路由通过构建时枚举生成，典型实现为 getStaticPaths。[S1][S2]

Node.js 仅用于本地／CI 构建，不要求访客访问时运行 Node 服务器。

默认 Astro 组件 + CSS + 少量 TypeScript/JavaScript。除非有明确用途与成本说明，不增加 React/Vue 全站水合、复杂状态库、重型动效库、WebGL 或服务端适配器。

### 10.2 建议结构

```text

  styles/
public/

tests/
astro.config.mjs

README.md

CONTENT_GUIDE.md

TEST_REPORT.md
KNOWN_ISSUES.md
```

目录是建议，不要求为了贴合目录增加空文件。所选 Astro、Node 和依赖版本必须记录并锁定兼容范围。

### 10.3 命令与可重复交付

项目需要定义并实际跑通依赖安装、开发、类型／内容检查、生产构建、预览和测试命令。可统一为 npm ci、npm run dev、npm run check、npm run build、npm run preview、npm test；采用其他包管理器时给出对应命令。

必须在生产构建产物上验收，不只在开发服务器检查。多页面 Astro 项目通过本地 HTTP 预览；不能把“在手机附件预览器打开 HTML”作为正式网站部署成功的证明。

## 11. 响应式与可访问性

### 11.1 布局测试

至少覆盖 320、360/390、430、768/820、1024、1366、1440/1920 CSS px，并在断点之间随机检查宽度；测试手机横屏与桌面 200% 缩放。

电脑、平板、手机可采用不同列数和字阶，但不机械按设备套 3／2／1 列。验收重点是作品完整、名称可读、正文舒适、交互可达。

禁止通过全局 overflow-x:hidden 掩盖真实布局溢出。不能仅在几个截图宽度看起来正常，中间宽度发生覆盖。

移动端要处理刘海／底部安全区、动态浏览器工具栏、弹窗滚动和关闭按钮位置，不锁定不合理的固定屏幕高度。

### 11.2 键盘与辅助技术

语义化使用链接、按钮、标题、main、nav 和图片说明；键盘焦点清楚，触屏不能依赖 hover。

如有模态看图：焦点应进入模态，Tab／Shift+Tab 不应跳到背景页面，Esc 可关闭，关闭后恢复合理焦点和原位置，屏幕阅读器应得到正确名称。[S13]

页面阅读不能因禁用 JS、关动效或某张图片失败而整体不可用。完整图库、正文和基础链接应有静态内容兜底；动态筛选等增强失效时可退回未筛选列表。

浏览器范围至少包含 Chromium、Firefox、WebKit 引擎自动化检查；正式移动验证需包含真实 iOS Safari。Playwright 的 WebKit 测试不应被写成“已完成 iPhone 真机测试”。有条件再检查 Android Chrome 与微信内置浏览器，并如实标记范围。

## 12. 性能预算与测量口径

以下是本项目建议基线，不是托管平台保证，也不是未测就可以声称达到的结果。

### 12.1 建议预算

| 项目 | 初始目标 |
|---|---|
| 首页冷缓存初始传输 | 移动端约 ≤1.5 MB；桌面约 ≤2.5 MB |
| 总览冷缓存初始传输 | 约 ≤2 MB；不要求加载全部作品 |
| 单幅详情初始传输 | 约 ≤2.5 MB；不含用户主动加载的高清细节 |
| 关键代码／字体等非图片资源 | 压缩传输合计优先控制在 300 KB 内 |
| 客户端 JavaScript | 压缩传输优先控制在 100 KB 内 |
| 单张总览缩略图 | 常见目标 40–180 KB，复杂笔触可例外评估 |
| 单张普通展示图 | 常见目标 200–900 KB，画质优先并记录例外 |

MB／KB 在报告中明确用十进制还是二进制，勿混用；预算表按近似十进制理解。具体值拿到真实作品后复核，需要放宽必须写原因与影响。

### 12.2 测量约定

记录浏览器版本、设备／DPR、视口、限速方式、缓存、测试路径、数据集和构建版本。初始传输量指冷缓存打开后前 5 秒、不滚动、不点击的所有资源实际传输，且同时检查未完成／排队请求；不能利用慢网或强制延迟把请求挪到 5 秒后制造达标。

额外记录滚动完整作品库和连续打开 5 件详情的传输量、失败请求及重复请求。首次访问和热缓存回访分别报告，不混为一谈。

Core Web Vitals 参考目标：LCP ≤2.5 秒、CLS ≤0.1、INP ≤200 ms。真实体验评估使用第 75 百分位口径；实验室测试与线上真实访客数据必须区分，没有现场数据不能假报 INP 已达标。[S14]

Lighthouse 得分仅作辅助，不代替真实设备、真实图像质量和大陆网络验证。不能为追求分数牺牲画作清晰度或删掉主要内容。

### 12.3 硬性网络底线

无论预算如何调整，未进入详情／细节时不得批量请求相应大图，更不得出现母版传输。无故重复预取、资源死循环和一次下载全站高清图属于阻断问题。

## 13. 托管、迁移、中国大陆访问与费用

### 13.1 部署候选

初期可使用 GitHub Pages 或 Cloudflare Pages。选择依据是部署便利和实际访问结果，不承诺任何免费政策永久不变，也不把某个平台的全球 CDN 等同于大陆稳定性保证。

网站采用可移植静态产物。站点域名 site、基础路径 base、图片资源域名应集中配置；不得在组件中到处写死 GitHub／Cloudflare／OSS 地址。

GitHub 项目站可能位于仓库子路径，必须处理 base 和全部内部链接；换成独立域名时需重新核对路径配置。[S5]

GitHub Pages 官方目前列有发布站点大小 1 GB、每月 100 GB 软带宽限制；Cloudflare Pages 也有部署与文件等平台限制。上线时再次核对，并根据实际产物规模评估，不能把“免费静态托管”理解为无限资源。[S6][S15]

### 13.2 阿里云 OSS 备选

迁移目标是保留页面、内容和组件，允许修改部署配置并重新构建，不要求重写网站。

不得承诺“同一个 dist 在所有平台无须设置就直接可用”。必须核对自定义域名、DNS、HTTPS、目录首页、尾斜杠、404 状态、MIME、缓存和静态资源路径。

使用 OSS 网站托管需核对自定义域名规则；中国大陆地域的 OSS 自定义域名涉及 ICP 备案要求，应以当时官方文档和实际接入条件确认。[S8]

国内 CDN 如启用，也要独立确认接入要求、备案和计费；不把 OSS 存储费当成所有网站费用。

### 13.3 大陆访问验证

Cloudflare China Network 是面向 Enterprise 客户的独立订阅，不能认为普通免费 Pages 自动使用中国大陆节点。[S7]

正式验证应记录访问地点、运营商、时间、设备和网址。在主要目标地区，尽量覆盖至少两地、两种接入网络、不同日期及晚间时段；样本不足必须披露。

检查首页、作品总览、直接打开详情、大图加载、资源失败、DNS／TLS／首字节时间及全路径操作。单次成功打开、海外测试或仅 Ping 通都不能得出“大陆访问稳定”的结论。

没有大陆测试条件时，交付状态写“静态站已部署，大陆访问未验证”，不能写“全面上线验收通过”。如持续出现页面打不开或核心资源失败，再依据测量选择备用托管。

### 13.4 成本与缓存

估算按“真实平均每次访问传输量 × 访问次数”计算，并区分存储、请求、源站出网、CDN 下行、回源、域名和可能的证书／附加服务费用。

例如 1,000 次访问 × 平均 5 MB 约为 5 GB，只是计算示例，不是流量预测或报价。

启用按量服务前明确预算、告警、异常流量应对及是否有真正硬上限。告警不能被当作绝对费用封顶保证。

内容哈希资源与 HTML 应使用适当不同的缓存策略；迁移和发布时避免旧 HTML 引用已删除图片／脚本。保留回滚版本、旧资源过渡方案和复测记录。

## 14. SEO、分享、公开范围与安全

每个正式作品页有独立 title、description、canonical、可见标题与正文、合适的图片 alt 和社交分享元数据。生成包含全部已发布内容的 sitemap 与合理 robots 配置；结构化数据仅使用已确认事实。

canonical／分享图片地址必须对应当前正式域名和部署路径，不残留测试域名。不存在的作品应进入真实 404 行为，不能用首页伪装所有不存在的页面。

预览站可设置 noindex，但未授权作品和私人资料不因 noindex 就获得保密保障；默认不公开这些资料。演示数据必须清楚标识，并在生产发布中排除。

不在源码、前端环境变量或发布包中包含密钥、完整母版、私人联系方式、未公开故事、聊天记录或合同文件。不默认加入分析追踪、第三方插件或外部表单。

## 15. 目标驱动自检机制

### 15.1 工作闭环

每个模块都按以下步骤执行：

**明确目标 → 写验收动作 → 实现 → 构建 → 真实运行 → 观察结果 → 记录失败 → 修复 → 回归测试。**

编译通过只是检查之一。不得用组件数量、代码行数、占位截图或“按钮存在”证明目标完成。

视觉效果必须在浏览器真实渲染中查看。网络性能必须检查实际请求。静态部署必须访问深层链接并刷新。用户此前发现的问题必须作为固定回归用例保留。

### 15.2 需求追踪

建立 REQUIREMENTS.md 或等效表格，每项含：

```text
需求编号
优先级
用户目标
实现位置／提交版本
验证步骤
预期结果
实际结果
证据文件
状态：通过／失败／未测试／受阻／不适用（说明原因）
后续处理
```

初始状态为“未测试”，不能预填通过。任何后续代码改动涉及已通过目标时，需要相关回归。

### 15.3 证据要求

保存实际浏览器截图／必要录屏、自动化测试报告、构建日志、网络记录或 HAR、图像清单、测试环境和构建版本。不能用设计稿、AI 生成效果图或旧版本截图冒充当前运行截图。

自动截图不等于人工视觉检查；截图需实际查看溢出、裁切、字号、按钮位置、空白和作品比例。轻量占位测试不能宣称通过真实油画画质／传输验收。

测试不存在的环境要写未测试。不能凭桌面 Chromium 推断 iPhone Safari，也不能凭本地测试推断中国大陆网络。

### 15.4 反例与失败场景

除了正常数据，至少用以下场景尝试破坏实现：0 件、1 件、50 件、60 件作品；独立 URL 缺失；极横／极竖图；标题极长；故事为空或约 3,000 字；图片损坏；没有年份／系列；同名不同 ID；重复 slug；空筛选；快速点击 10 次；网络慢／失败；脚本失败；关动效；缓存回访；子路径部署。

测试数据与正式数据分离。0 件或 1 件作品可以用于组件测试，不代表正式作品集已完成。

## 17. 阶段计划与完成边界

### 阶段 A：结构与交互版本

当前可以推进：Astro 项目、多页面路由、统一 SVG、正确入口、占位作品数据、独立详情、响应式与核心自动测试。用 6–10 个不同画幅占位验证设计，再用约 50 个独立条目验证规模。

交付时写“结构／交互版本”，明确真实图像质量、正式视觉和大陆网络尚未验收。

### 阶段 B：真实作品接入与视觉定稿

获得代表作和基础资料后，比较候选方向、批准视觉语言、处理全部网页图片、录入内容。复查原型中在色块上不明显的拥挤、明暗冲突和画质问题。

### 阶段 C：正式发布

确认文案授权、数据完整度、真实图像预算、正式域名、目标托管配置和大陆访问测试。P0 全部通过；P1 未完成项必须明确处理并得到项目方确认，不能未经说明称为全面完成。

### 必须暂停发布的情况

深层详情刷新失败；母版／私密数据公开；总览请求全部高清图；核心导航或手机按钮失效；严重作品错配／色彩损坏；发布假履历／假故事；真实图片质量不满足观看；正式主域名或关键资源反复无法访问。

技术原型可以阶段性交付，但不能把这些阻断项改名为“后续优化”掩盖。

## 19. 待确认资料与默认处理

| 待确认 | 现在怎么推进 |
|---|---|
| 真实作品图和代表作 | 用清楚标注的占位图做结构；不伪造艺术家油画 |
| 标题、年份、媒介、尺寸与系列 | 建好字段和校验，未知值留空，不填假事实 |
| 创作故事与心境 | 支持长正文模板，正式文案等待客户提供／批准 |
| 艺术家简介、照片和展览 | 预留内容能力，不编履历，不发布空展览页 |
| 正式语言与双语范围 | 文案集中管理，先支持中英文长度，不强行全站双语 |
| 联系方式、域名及预算 | 配置留空／演示标识，不购买、不修改 DNS、不连接收费服务 |
| 高清开放程度与公开授权 | 默认仅网页展示图，母版不公开 |
| 网站最终艺术方向 | 等代表作对照后由项目方确认 |
| 大陆主要访问地区与设备 | 先准备测试清单，上线前获取实际样本 |

缺少最终素材不应阻止搭建可验证骨架；也不能成为编造内容或宣布正式设计已完成的理由。

## 20. 给后续 AI／开发者的执行指令

> 以本文件为需求基线，使用 Astro 完成 Jiang Qiao Yan 的多页面静态油画作品集。先建立需求追踪与验收用例，再开发首页、全部作品页和作品独立详情；不要仅修改现有单页演示，也不要新增无必要后端。
>
> 优先消除用户已报告的 SVG／emoji 图标问题和作品入口定位问题。真实素材缺失时使用明确标识的占位数据，同时建立支持 40–50 件作品、长故事和多种画幅的数据与图片管线。
>
> 每完成一个模块，都必须实际运行并检查用户目标：链接是否到正确位置、图像是否按需加载、独立页面是否可直接刷新、手机是否可用、作品是否被完整呈现。发现问题后修复并回归，不以代码写完代替验收。

> 当前阶段可以完成结构与交互，但不能把占位稿声称为已完成最终艺术视觉、正式图像质量或大陆网络验收。所有未测试和受阻事项必须明确保留。
>
> 交付完整项目、运行方法、数据维护方法、部署配置、需求追踪、真实测试证据和已知问题。除非明确获得授权，不购买服务、修改域名解析、公开客户未批准素材或连接收费后端。
